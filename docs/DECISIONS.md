# Decisions

One line per choice the spec left open.

## Milestone 1

- **Tooling:** `uv` installed with Homebrew; dependencies locked in `uv.lock`; the project is not packaged (`tool.uv.package = false`), and modules are imported from the repo root.
- **Added dependency:** `pytest-cov` (dev) measures the 80% `tools/` coverage that Milestone 2 requires. Approved by the user.
- **Added dependency:** `pyyaml` reads `schemas/*.yml`. Approved before work started.
- **Parquet:** written by DuckDB (`COPY ... TO ... (FORMAT parquet)`) with column types taken from the schema YAML, so `pyarrow`/`pandas` are not needed.
- **Fixed reference date:** generated dates are anchored to 2025-06-30 instead of today, so the same seed gives the same data on any day.
- **Determinism scope:** the same seed and dependency versions give byte-identical CSV, Parquet, and answer keys (verified by running `make seed` twice). Tests compare CSV bytes and Parquet contents.
- **Required columns:** every column is `required: true` except `country`, `canceled_at`, and `paid_at`. Amount, plan, status, and seats columns have no meaning when empty, even though §7.1 does not say "Required".
- **Clean nulls:** about 2% of customers have no `country`, so `null_variants` has real nulls to render in every table.
- **Volumes:** about 1.2 subscriptions per customer and about 4.6 invoices per subscription (invoices stop at the reference date or the cancellation date).
- **Date ambiguity:** `mixed_date_formats` always uses US `MM/DD/YYYY`, plus at most one unambiguous format (`DD Mon YYYY`, `YYYYMMDD`, `Month DD, YYYY`). Slash dates are always month first.
- **Defect vocabulary:** answer keys, the agent, and the app database share the fixed `DefectType` enum in `agent/defects.py` (moved from `evals/corrupt.py` in Milestone 3): `duplicate_rows`, `null_variants`, `type_noise`, `value_drift`, `mixed_date_formats`, `merged_column`, `missing_required_column`.
- **Defects vs. mapping challenges:** `rename_columns`, `cryptic_names`, and `extra_columns` are mapping problems, not defects. Extra columns go in `unmapped_source_columns`, and the renames show up in `mappings`.
- **Merged columns:** one source column maps to two targets, and each mapping entry has `merged: {separator, part}`. Pairs come from a fixed list of plausible pairs per table (for example `plan`+`status`, `invoice_date`+`due_date`).
- **Column claiming:** each value-level corruption, merge, and drop takes a different column, so every defect's `affected_rows` is exact. If a planned extra corruption has no free column left, it is dropped from the case.
- **Duplicates:** about half of the duplicate rows differ from the original only by casing or whitespace in a free-text column (IDs included). `affected_rows` counts the extra rows; `details.duplicate_of` pairs each extra row with the row it copies.
- **Type noise:** about 2% of noised cells become unparseable junk (`N/A`, `TBD`, …), listed by row number in `details.unparseable_rows`. In required columns these rows should end up rejected.
- **Row numbers in answer keys:** every row-level defect lists its affected rows as 1-based messy-file row numbers in `rows`, the same numbering as `_row` in the warehouse. Column-wide defects (`merged_column`, `missing_required_column`) have `rows: null`.
- **Case layout:** `evals/cases/<case_id>/` holds `messy.csv`, `clean.csv` (the sampled clean rows, used as truth for cell accuracy), and `answer_key.json`.
- **Case plan:** each table's 10 cases cycle through all 10 corruption types as the primary one, plus 0–3 random extras, so every type appears at least once per table. At least 7 of each table's 10 cases rename columns (`rename_columns` or `cryptic_names`), because cases that keep target names make mapping trivially easy. `names_changed` in the answer key lets the scorecard report both groups separately.
- **Makefile:** only targets that work today (`seed`, `test`, `lint`, `format`). `up`, `down`, `eval`, `eval-smoke`, and `onboard` are added in the milestones that implement them.

## Milestone 2

- **Added dependencies:** `sqlglot` and `pydantic`, both listed in §4 of the spec. Tool results are Pydantic models, so the agent and the MCP server can serialize them to JSON.
- **Extra module:** `tools/warehouse.py` owns the per-run DuckDB file, loading files into `raw`, and the file registry. Profiling and transforms both depend on it.
- **Tool metadata lives in the warehouse:** `meta.files` and `meta.column_profiles` sit in the run's DuckDB file, so the tools work on DuckDB alone (in-process or over MCP). The app database copies them from Milestone 3 onward.
- **file_id:** the first 16 hex characters of the file's sha256. Loading identical content again, even under another name, returns the existing file and creates no new table.
- **Raw tables:** `raw.<sanitized stem>` (`_2`, `_3`, … if the name is taken), every column text, plus `_row` = 1-based source row number. A source column named `_row` is rejected.
- **Supported inputs (for now):** `.csv`, `.tsv`, `.txt` (delimiter auto-detected, UTF-8) and `.parquet`. Upload limits and encoding handling come with the API in Milestone 5.
- **Nulls:** empty and whitespace-only cells count as null. Text such as `N/A`, `NULL`, `-` is reported separately as `null_like_count` and is left out when inferring types.
- **Type inference:** the type matching the largest share of real values wins (ties go to the more specific type: boolean, integer, decimal, date, timestamp). Below 50%, the column is `varchar`. `type_match_rate` reports the share. Only ISO dates count as `date`; other formats show up in patterns.
- **Patterns:** named shapes first (date formats, numbers, currency, booleans, email, null-like text), else a generic shape (`CUS-000001` → `A-999999`). Leading or trailing whitespace adds `(padded)`. The top 12 shapes are kept and the rest summed under `other shapes`. Slash dates are named `MM/DD/YYYY` or `DD/MM/YYYY` only when some value in the column settles the order; otherwise `NN/NN/YYYY`.
- **sample_rows:** `n` above 20 is capped at 20, not rejected. Rows are picked by `hash(_row)` (spread across the file, the same on every call) and returned in source order. Cells longer than 200 characters are truncated.
- **SQL safety:** model SQL is parsed with sqlglot and must be one expression (no statements, subqueries, table references, `*`, aggregates, window functions, lambdas or parameters). It may only use bare column names from the file. Functions are refused if they read files, settings, or the catalog; if they are not deterministic; or if they build arbitrarily large values (`repeat`, `range`, `generate_series`, list resizing). The SQL sqlglot regenerates (without comments) is what runs, on a read-only connection with external access disabled. `sample_rows(where=...)` uses the same check.
- **Query limits:** model-influenced queries are interrupted after `TOOL_QUERY_TIMEOUT_SECONDS` (default 60), and read-only connections are capped at `TOOL_MEMORY_LIMIT` (default 2GB). DuckDB's memory limit covers joins, sorts, and aggregates but not per-row string temporaries, which is why the large-value functions above are refused and the timeout backs everything up.
- **test_transform:** a row counts as input when any referenced column is non-blank. `success_rate = converted / non_null_input`; failures are split into `null_output` (the expression returned NULL) and `cast_failed` (output does not cast to the target type), with up to 5 examples in row order. An expression that errors at runtime (e.g. a strict `::date`) is reported as a tool error suggesting `try_cast`/`try_strptime`.
- **Coverage gate:** `make test` fails if `tools/` line coverage drops below 80%.

## Milestone 3

- **Added dependencies:** `openai`, `sqlalchemy`, `alembic` (from §4), and `mlflow-skinny`, the official MLflow client package without the server and UI dependencies (pandas, scikit-learn, Flask, …). The MLflow server image arrives with Compose in Milestone 5.
- **MLflow store:** traces go to `sqlite:///data/mlflow.db` by default. MLflow 3 puts the plain-file `./mlruns` store in maintenance mode and refuses tracing on it; SQLite is still a single local file. View with `uvx mlflow ui --backend-store-uri sqlite:///data/mlflow.db`.
- **Local model:** `qwen3:8b` through Ollama's OpenAI-compatible endpoint. Ollama serves a 4,096-token context by default and silently drops the start of longer conversations; the Map phase starts at about 3.4k tokens. So `make model` builds `qwen3-8b-16k` from `ollama/qwen3-8b-16k.Modelfile` (same weights, `num_ctx 16384`). The code does not know about either model; `LLM_MODEL` picks it.
- **Thinking mode:** `LLM_REASONING_EFFORT` (optional) is passed through as `reasoning_effort`; `none` turns off qwen3's thinking, which cuts one mapping from about 200 s to tens of seconds.
- **Default settings outside Compose:** `LLM_BASE_URL` defaults to `http://localhost:11434/v1`, `DATABASE_URL` to `sqlite:///data/app.db`, and `MLFLOW_TRACKING_URI` to `sqlite:///data/mlflow.db`, so `make onboard` works with no configuration besides `LLM_MODEL`. `LLM_MODEL` has no default; the CLI exits with a message when it is unset.
- **`.env` loading:** `Settings.from_env()` reads `.env` from the working directory with a small built-in parser (no `python-dotenv`). It only fills variables that are not already set, so a real environment variable wins. For local runs, keep `.env` to the `LLM_*` lines: the Compose values in `.env.example` (`postgres`, `mlflow` hostnames) do not resolve outside Docker.
- **Hosted model (OpenRouter):** Ollama runs overheated the development laptop, so evals and CLI runs use OpenRouter through the same OpenAI-compatible client: `LLM_BASE_URL=https://openrouter.ai/api/v1`, `LLM_MODEL=qwen/qwen3-32b`. This departs from the spec's zero-cost constraint (about $0.20 per full eval, approved by the user). Free `:free` models are capped at 50 requests a day without bought credits, and a full eval needs about 300. No code depends on the provider; Ollama remains the default and works unchanged.
- **Retries:** timeouts, connection errors, rate limits (429), and server errors (5xx) are retried 3 times with exponential backoff starting at `LLM_RETRY_BACKOFF_SECONDS` (default 5 s, so 5, 10, 20 s); the SDK's own retries are off. Then the run fails with the reason. Other API errors (bad key, unknown model, no credit) fail the run at once with the provider's message.
- **Step counting:** a step is one model call. A reply without a tool call costs a step and gets a nudge to call a tool.
- **Map phase input:** the first user message carries compact profiles of every source column (type, nulls, distinct count, top 5 values, top 4 patterns) and the full target schema, so a small model does not spend turns fetching them. The tools still offer `get_target_schema`, `get_column_profile`, `sample_rows`, `test_transform`, `submit_mappings` (5 tools).
- **Missing required columns:** `submit_mappings` accepts `missing_required: [{target_column, reason}]`. Without it, a file that truly lacks a required column could never pass the "missing required columns" check. Each declared target is stored as a mapping row with no source column, waiting for review.
- **More validation:** besides the spec's checks, a mapping's `transform_sql` must read its own `source_column`, and defects must name real columns.
- **Derived defects:** a source column mapped to two targets is recorded as `merged_column`, and each declared missing target as `missing_required_column`, when the model did not report them. Both follow directly from the accepted mapping.
- **Review routing:** mapping `status` is `approved` when auto-approved and `proposed` when it waits for a human; `review_reason` says why (low confidence, or no source column). `NULL` means auto-approved.
- **Run statistics:** `runs` also stores `trace_id`, model and tool call counts, token counts, and duration, for the report and the scorecard.
- **Scoring:** mapping accuracy compares each source column's set of predicted targets with the answer key's (both targets of a merged column must be found; extra columns must stay unmapped). A failed run counts every mapped source column as wrong. Defects match on type and column, except `duplicate_rows`, which matches on type alone because it is a table-level defect. All rates are micro-averaged over every case. A bad auto-approval is a mapping with confidence at or above the threshold that the answer key does not contain.
- **Eval isolation:** `make eval` writes its runs to `data/evals/` (warehouses and its own `app.db`) so eval runs do not mix with CLI runs, and logs one MLflow run per eval (experiment `data-onboarding-evals`, tagged with the model) with each case's trace linked to it.
- **eval-smoke:** `FakeLLM` answers each case from its answer key after calling two tools. This exercises loading, profiling, the loop, validation, persistence, and scoring end to end; the command fails unless every score is perfect. CI runs `make seed` first.
- **First scorecard:** `evals/results/20261126T212849Z_qwen-qwen3-32b.md` (OpenRouter, thinking on by default) was produced by commit `2231b17`. An earlier local run on `qwen3-8b-16k` was stopped after 13 of 30 cases and wrote no scorecard.
- **Single quotes for text:** in the local run, two cases failed at the step limit because the model wrote `split_part("c", "|", 1)`, which SQL reads as a column named `|`, and repeated the same call 22 times. After the first scorecard, the unknown-column error now tells the model to use single quotes when the unknown name was double-quoted, and the prompt states the rule.
