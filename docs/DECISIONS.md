# Decisions

One line per choice the spec left open.

## Milestone 1

- **Tooling:** `uv` installed with Homebrew; dependencies locked in `uv.lock`; the project is not packaged (`tool.uv.package = false`), and modules are imported from the repo root.
- **Added dependency:** `pytest-cov` (dev) measures the 80% `tools/` coverage that Milestone 2 requires. Approved by the user.
- **Added dependency:** `pyyaml` reads `schemas/*.yml`. Approved before work started.
- **Parquet:** written by DuckDB (`COPY ... TO ... (FORMAT parquet)`) with column types taken from the schema YAML, so `pyarrow`/`pandas` are not needed.
- **Fixed reference date:** generated dates are anchored to 2025-06-30 instead of today, so the same seed gives the same data on any day.
- **Determinism scope:** the same seed and dependency versions give byte-identical CSV, Parquet, and answer keys (verified by running `make seed` twice). Tests compare CSV bytes and Parquet contents.
- **Required columns:** every column is `required: true` except `country`, `canceled_at`, and `paid_at`. Amount, plan, status, and seats columns have no meaning when empty, even though §7.1 does not say "Required".
- **Clean nulls:** about 2% of customers have no `country`, so `null_variants` has real nulls to render in every table.
- **Volumes:** about 1.2 subscriptions per customer and about 4.6 invoices per subscription (invoices stop at the reference date or the cancellation date).
- **Date ambiguity:** `mixed_date_formats` always uses US `MM/DD/YYYY`, plus at most one unambiguous format (`DD Mon YYYY`, `YYYYMMDD`, `Month DD, YYYY`). Slash dates are always month first.
- **Defect vocabulary:** answer keys, the agent, and the app database share the fixed `DefectType` enum in `agent/defects.py` (moved from `evals/corrupt.py` in Milestone 3): `duplicate_rows`, `null_variants`, `type_noise`, `value_drift`, `mixed_date_formats`, `merged_column`, `missing_required_column`.
- **Defects vs. mapping challenges:** `rename_columns`, `cryptic_names`, and `extra_columns` are mapping problems, not defects. Extra columns go in `unmapped_source_columns`, and the renames show up in `mappings`.
- **Merged columns:** one source column maps to two targets, and each mapping entry has `merged: {separator, part}`. Pairs come from a fixed list of plausible pairs per table (for example `plan`+`status`, `invoice_date`+`due_date`).
- **Column claiming:** each value-level corruption, merge, and drop takes a different column, so every defect's `affected_rows` is exact. If a planned extra corruption has no free column left, it is dropped from the case.
- **Duplicates:** about half of the duplicate rows differ from the original only by casing or whitespace in a free-text column (IDs included). `affected_rows` counts the extra rows; `details.duplicate_of` pairs each extra row with the row it copies.
- **Type noise:** about 2% of noised cells become unparseable junk (`N/A`, `TBD`, …), listed by row number in `details.unparseable_rows`. In required columns these rows should end up rejected.
- **Row numbers in answer keys:** every row-level defect lists its affected rows as 1-based messy-file row numbers in `rows`, the same numbering as `_row` in the warehouse. Column-wide defects (`merged_column`, `missing_required_column`) have `rows: null`.
- **Case layout:** `evals/cases/<case_id>/` holds `messy.csv`, `clean.csv` (the sampled clean rows, used as truth for cell accuracy), and `answer_key.json`.
- **Case plan:** each table's 10 cases cycle through all 10 corruption types as the primary one, plus 0–3 random extras, so every type appears at least once per table. At least 7 of each table's 10 cases rename columns (`rename_columns` or `cryptic_names`), because cases that keep target names make mapping trivially easy. `names_changed` in the answer key lets the scorecard report both groups separately.
- **Makefile:** only targets that work today (`seed`, `test`, `lint`, `format`). `up`, `down`, `eval`, `eval-smoke`, and `onboard` are added in the milestones that implement them.

## Milestone 2

- **Added dependencies:** `sqlglot` and `pydantic`, both listed in §4 of the spec. Tool results are Pydantic models, so the agent and the MCP server can serialize them to JSON.
- **Extra module:** `tools/warehouse.py` owns the per-run DuckDB file, loading files into `raw`, and the file registry. Profiling and transforms both depend on it.
- **Tool metadata lives in the warehouse:** `meta.files` and `meta.column_profiles` sit in the run's DuckDB file, so the tools work on DuckDB alone (in-process or over MCP). The app database copies them from Milestone 3 onward.
- **file_id:** the first 16 hex characters of the file's sha256. Loading identical content again, even under another name, returns the existing file and creates no new table.
- **Raw tables:** `raw.<sanitized stem>` (`_2`, `_3`, … if the name is taken), every column text, plus `_row` = 1-based source row number. A source column named `_row` is rejected.
- **Supported inputs (for now):** `.csv`, `.tsv`, `.txt` (delimiter auto-detected, UTF-8) and `.parquet`. Upload limits and encoding handling come with the API in Milestone 5.
- **Nulls:** empty and whitespace-only cells count as null. Text such as `N/A`, `NULL`, `-` is reported separately as `null_like_count` and is left out when inferring types.
- **Type inference:** the type matching the largest share of real values wins (ties go to the more specific type: boolean, integer, decimal, date, timestamp). Below 50%, the column is `varchar`. `type_match_rate` reports the share. Only ISO dates count as `date`; other formats show up in patterns.
- **Patterns:** named shapes first (date formats, numbers, currency, booleans, email, null-like text), else a generic shape (`CUS-000001` → `A-999999`). Leading or trailing whitespace adds `(padded)`. The top 12 shapes are kept and the rest summed under `other shapes`. Slash dates are named `MM/DD/YYYY` or `DD/MM/YYYY` only when some value in the column settles the order; otherwise `NN/NN/YYYY`.
- **sample_rows:** `n` above 20 is capped at 20, not rejected. Rows are picked by `hash(_row)` (spread across the file, the same on every call) and returned in source order. Cells longer than 200 characters are truncated.
- **SQL safety:** model SQL is parsed with sqlglot and must be one expression (no statements, subqueries, table references, `*`, aggregates, window functions, lambdas or parameters). It may only use bare column names from the file. Functions are refused if they read files, settings, or the catalog; if they are not deterministic; or if they build arbitrarily large values (`repeat`, `range`, `generate_series`, list resizing). The SQL sqlglot regenerates (without comments) is what runs, on a read-only connection with external access disabled. `sample_rows(where=...)` uses the same check.
- **Query limits:** model-influenced queries are interrupted after `TOOL_QUERY_TIMEOUT_SECONDS` (default 60), and read-only connections are capped at `TOOL_MEMORY_LIMIT` (default 2GB). DuckDB's memory limit covers joins, sorts, and aggregates but not per-row string temporaries, which is why the large-value functions above are refused and the timeout backs everything up.
- **test_transform:** a row counts as input when any referenced column is non-blank. `success_rate = converted / non_null_input`; failures are split into `null_output` (the expression returned NULL) and `cast_failed` (output does not cast to the target type), with up to 5 examples in row order. An expression that errors at runtime (e.g. a strict `::date`) is reported as a tool error suggesting `try_cast`/`try_strptime`.
- **Coverage gate:** `make test` fails if `tools/` line coverage drops below 80%.

## Milestone 3

- **Added dependencies:** `openai`, `sqlalchemy`, `alembic` (from §4), and `mlflow-skinny`, the official MLflow client package without the server and UI dependencies (pandas, scikit-learn, Flask, …). The MLflow server image arrives with Compose in Milestone 5.
- **MLflow store:** traces go to `sqlite:///data/mlflow.db` by default. MLflow 3 puts the plain-file `./mlruns` store in maintenance mode and refuses tracing on it; SQLite is still a single local file. View with `uvx mlflow ui --backend-store-uri sqlite:///data/mlflow.db`.
- **Local model:** `qwen3:8b` through Ollama's OpenAI-compatible endpoint. Ollama serves a 4,096-token context by default and silently drops the start of longer conversations; the Map phase starts at about 3.4k tokens. So `make model` builds `qwen3-8b-16k` from `ollama/qwen3-8b-16k.Modelfile` (same weights, `num_ctx 16384`). The code does not know about either model; `LLM_MODEL` picks it.
- **Thinking mode:** `LLM_REASONING_EFFORT` (optional) is passed through as `reasoning_effort`; `none` turns off qwen3's thinking, which cuts one mapping from about 200 s to tens of seconds.
- **Default settings outside Compose:** `LLM_BASE_URL` defaults to `http://localhost:11434/v1`, `DATABASE_URL` to `sqlite:///data/app.db`, and `MLFLOW_TRACKING_URI` to `sqlite:///data/mlflow.db`, so `make onboard` works with no configuration besides `LLM_MODEL`. `LLM_MODEL` has no default; the CLI exits with a message when it is unset.
- **`.env` loading:** `Settings.from_env()` reads `.env` from the working directory with a small built-in parser (no `python-dotenv`). It only fills variables that are not already set, so a real environment variable wins. For local runs, keep `.env` to the `LLM_*` lines: the Compose values in `.env.example` (`postgres`, `mlflow` hostnames) do not resolve outside Docker.
- **Hosted model (OpenRouter):** Ollama runs overheated the development laptop, so evals and CLI runs use OpenRouter through the same OpenAI-compatible client: `LLM_BASE_URL=https://openrouter.ai/api/v1`, `LLM_MODEL=qwen/qwen3-32b`. This departs from the spec's zero-cost constraint (about $0.20 per full eval, approved by the user). Free `:free` models are capped at 50 requests a day without bought credits, and a full eval needs about 300. No code depends on the provider; Ollama remains the default and works unchanged.
- **Retries:** timeouts, connection errors, rate limits (429), and server errors (5xx) are retried 3 times with exponential backoff starting at `LLM_RETRY_BACKOFF_SECONDS` (default 5 s, so 5, 10, 20 s); the SDK's own retries are off. Then the run fails with the reason. Other API errors (bad key, unknown model, no credit) fail the run at once with the provider's message.
- **Step counting:** a step is one model call. A reply without a tool call costs a step and gets a nudge to call a tool.
- **Map phase input:** the first user message carries compact profiles of every source column (type, nulls, distinct count, top 5 values, top 4 patterns) and the full target schema, so a small model does not spend turns fetching them. The tools still offer `get_target_schema`, `get_column_profile`, `sample_rows`, `test_transform`, `submit_mappings` (5 tools).
- **Missing required columns:** `submit_mappings` accepts `missing_required: [{target_column, reason}]`. Without it, a file that truly lacks a required column could never pass the "missing required columns" check. Each declared target is stored as a mapping row with no source column, waiting for review.
- **More validation:** besides the spec's checks, a mapping's `transform_sql` must read its own `source_column`, and defects must name real columns.
- **Derived defects:** a source column mapped to two targets is recorded as `merged_column`, and each declared missing target as `missing_required_column`, when the model did not report them. Both follow directly from the accepted mapping.
- **Review routing:** mapping `status` is `approved` when auto-approved and `proposed` when it waits for a human; `review_reason` says why (low confidence, or no source column). `NULL` means auto-approved.
- **Run statistics:** `runs` also stores `trace_id`, model and tool call counts, token counts, and duration, for the report and the scorecard.
- **Scoring:** mapping accuracy compares each source column's set of predicted targets with the answer key's (both targets of a merged column must be found; extra columns must stay unmapped). A failed run counts every mapped source column as wrong. Defects match on type and column, except `duplicate_rows`, which matches on type alone because it is a table-level defect. All rates are micro-averaged over every case. A bad auto-approval is a mapping with confidence at or above the threshold that the answer key does not contain.
- **Eval isolation:** `make eval` writes its runs to `data/evals/` (warehouses and its own `app.db`) so eval runs do not mix with CLI runs, and logs one MLflow run per eval (experiment `data-onboarding-evals`, tagged with the model) with each case's trace linked to it.
- **eval-smoke:** `FakeLLM` answers each case from its answer key after calling two tools. This exercises loading, profiling, the loop, validation, persistence, and scoring end to end. CI runs `make seed` first.
- **First scorecard:** `evals/results/20261126T212849Z_qwen-qwen3-32b.md` (OpenRouter, thinking on by default) was produced by commit `2231b17`. An earlier local run on `qwen3-8b-16k` was stopped after 13 of 30 cases and wrote no scorecard.
- **Single quotes for text:** in the local run, two cases failed at the step limit because the model wrote `split_part("c", "|", 1)`, which SQL reads as a column named `|`, and repeated the same call 22 times. After the first scorecard, the unknown-column error now tells the model to use single quotes when the unknown name was double-quoted, and the prompt states the rule.

## Milestone 4

- **dbt 1.11, not 2.0:** `dbt-core>=1.11,<1.12` and `dbt-duckdb`. dbt-core 1.12 and 2.0 depend on `dbt-core-experimental-parser`, whose build step downloads a native wheel with Python's `urllib`, which fails on this machine's certificate store. 1.11 is pure Python and works with DuckDB 2.0. `jinja2` is listed explicitly because our templates use it directly.
- **dbt runs from the venv:** `run_dbt` calls the `dbt` next to `sys.executable`, never one on `PATH` (this machine has a global dbt Fusion binary). Anonymous usage stats are off in `dbt_project.yml` and through `DO_NOT_TRACK`, so builds make no network calls.
- **Project per run:** `data/runs/<run_id>/dbt/` holds the rendered project, logs, and `target/`. It is re-rendered from the approved mappings before every build, so it always matches the database.
- **Three models per target table:** `int_<table>__checked` (every source row, converted values, `reject_reason`), `stg_<table>` (clean rows, target columns plus `_file_id` and `_source_row` lineage), and `rejected_<table>` (reason plus the row's raw values as JSON). All are tables, so a rebuild replaces them and never duplicates rows.
- **Quarantine rules:** a row is rejected when a transform's output does not cast to the target type, when a transform returns NULL for a non-blank, non-null-token input, or when a required column is NULL; the reasons are joined with `; `. Of rows sharing a key, the first valid one (by file, then source row) is kept and the others get `duplicate <key>`. For a source column that feeds two targets (merged), only the cast check applies, because the merged text is non-blank even when one part is empty.
- **Allowed values are tested, not quarantined:** `accepted_values` failures fail the build and go to the repair agent, as in §10.6; quarantining them would hide every value-drift problem. Milestone 7 adds quarantine for new categories in recurring loads.
- **Model SQL is protected from dbt's Jinja:** the generated models are wrapped in `{% raw %}`, and a transform containing `endraw` is refused at render time.
- **Build phase tools:** `update_transform`, `run_dbt`, `get_dbt_errors`, `test_transform`, `submit_build`. The model is only called when the first build fails. Each `run_dbt` call counts as one repair; it ends the loop when the build passes or `BUILD_MAX_REPAIRS` is used up. A `run_dbt` with a `--select` that passes is followed by one full build before the run can pass.
- **Repairs are audited:** every `update_transform` writes a `review_events` row with `action = agent_repair`, the before and after state, and the model's reason.
- **Review step:** `agent/review.py` applies approve, edit, and reject decisions and records each in `review_events`; edits are validated like model SQL. The CLI's `--approve-all` approves everything pending (actor `cli`). A run builds only when no mapping is still `proposed`.
- **One trace per CLI or eval run:** `onboard(review=...)` profiles, maps, reviews, and builds under one MLflow trace. A run reviewed later (the API in Milestone 5) is built by `build_run`, which opens a second trace tagged with the same `run_id`; a trace cannot stay open while a human reviews.
- **Build report:** stored in `runs.build_report` (JSON): status, repairs, dbt pass and fail counts and node results, and row accounting with reject reasons per file. Adding the column means local SQLite databases from Milestone 3 must be deleted (`data/app.db`, `data/evals/app.db`); Alembic migrations arrive in Milestone 5.
- **Missing required column:** when a required target has no source, every row is quarantined with `missing required <column>`, and the build passes with zero rows loaded. That is what "quarantine, never drop" requires; a human who wants to load anyway must provide a mapping.
- **Eval review:** the answer key plays the human reviewer: proposed mappings it confirms are approved, the rest rejected, and declared-missing targets approved. Mappings the agent auto-approved are not reviewed, so a bad auto-approval flows into the build, which is exactly the risk the metric tracks.
- **Cell accuracy:** loaded values are compared with the clean table by key, after normalizing types (dates as ISO text, decimals to 2 places, booleans as true/false, NULL as empty). The denominator is every clean row times every target column, so quarantined rows, including the planted junk values, count as wrong. Perfect transforms therefore score below 100% on cases with junk or a dropped column.
- **Pass and consistency:** a run passes when every source column is mapped correctly and the build passes. `--repeats N` runs each case N times; consistency is the share of cases that pass on all N runs.
- **Oracle transforms for eval-smoke:** the FakeLLM oracle now writes cleaning SQL for every corruption type (null tokens, all date formats, number formatting, boolean words, value drift from the answer key's variants, ID casing), so `make eval-smoke` also requires every build to pass. It does not gate on cell accuracy, which is below 100% by design (see above).
- **eval module split:** `evals/scoring.py` (scores and metrics), `evals/oracle.py` (answer-key reviewer and FakeLLM), and `evals/run_evals.py` (harness and scorecard).
- **Milestone 4 scorecard:** `evals/results/20261126T224636Z_qwen-qwen3-32b.md` (OpenRouter `qwen/qwen3-32b`), produced by commit `3d9e836` with one run per case; consistency needs `--repeats 3` (about 2.5 hours) and was not run. Cell accuracy has a ceiling of about 86% on this case set, because 4 of 30 cases drop a required column and every one of their rows is quarantined.

## Milestone 5

- **Added dependencies:** `fastapi`, `uvicorn`, `mcp` (all in §4), plus what they need to work as the spec describes: `psycopg[binary]` (the driver in the spec's `postgresql+psycopg://` URL) and `python-multipart` (FastAPI's file uploads); `httpx` is a dev dependency for FastAPI's test client.
- **MCP SDK 2.x:** `MCPServer` (formerly `FastMCP`) over stateless streamable HTTP at `tools:8100/mcp`, with `GET /health` as a custom route. DNS-rebinding protection is off because Compose reaches the server as `tools:8100`; the port is only for the local stack. The SDK only passes a tool's error message to the client for its own `ToolError`, so `tools/server.py` translates our `ToolError` at the boundary; the tool functions stay free of MCP imports.
- **Tool backend:** the phases call tools through `RunTools`, implemented in-process (`LocalTools`, CLI and tests) and over MCP (`McpTools`, Compose, chosen when `TOOLS_URL` is set). Both return the same Pydantic models. A test runs a full onboarding with every data tool going over MCP. Loading uploads, rendering the dbt project, and row accounting stay in the API process; profiling, sampling, transform tests, and dbt runs go through the backend.
- **One image, shared volume:** `api` and `tools` use the same image and mount the same `run-data` volume at `/app/data`, so warehouse and dbt paths are identical in both. DuckDB allows one writer per file, so a run's tool calls are sequential; different runs use different files.
- **Alembic:** migrations in `api/migrations` run on API startup and in every `session_factory` call (SQLite in tests and CLI, Postgres in Compose). `create_all` is gone. A test checks the migrations match the models. Local SQLite databases created by earlier milestones must be deleted once.
- **State machine and resume:** `agent/runner.advance` runs whatever is due: profile files without stored profiles, map files without mappings, then build once `runs.reviewed_at` is set (review submitted with nothing pending). A failed run resumes with `POST /start` from its last completed phase; finished work is not redone (tested: profiles keep their ids after a resumed mapping). On API startup, runs left in profiling, mapping, or building by a crash are marked failed with a "POST /start to resume" message.
- **Profiles stored in full:** `column_profiles.profile` keeps the tool's whole profile (JSON) and `source_files.raw_table` the raw table name, so mapping after a resume and building read everything from the database instead of re-profiling or opening DuckDB from the API.
- **Background worker:** a two-thread pool inside the API process, as the spec puts the agent there. Each job has its own session; a run cannot be advanced twice at once (409). Tests run jobs inline.
- **Uploads:** validated while streaming to disk in 1 MB chunks: supported suffix (415), size within `MAX_UPLOAD_MB` (413), UTF-8 for text files with the offending byte and position in the message (422), Parquet magic bytes (422), not empty (422). Then the file is loaded into the warehouse, which rejects header-only files and parse errors (422). Rejected files are deleted. Files can be added only before mapping.
- **Review endpoint:** `POST /runs/{id}/review` applies approve, edit, and reject decisions (edits validated like model SQL, 422 when invalid) and starts the build once nothing is pending, unless `build: false`.
- **Health:** `GET /health` returns 200 only when the database answers `SELECT 1`, the model endpoint answers `/models` (and `LLM_MODEL` is set), and the tools server answers `/health`; otherwise 503 with each check's error. The api container's health check uses it, so the stack is only healthy with a configured model.
- **Logs:** the API writes one JSON object per line; lines written while a run is advanced carry its `run_id` (a context variable set by the worker).
- **MLflow port:** the container listens on 5000 as the spec says, published on host port 5001 because macOS's AirPlay Receiver holds 5000. The server needs `--allowed-hosts` for `mlflow:5000` and `localhost:5001`. Reports link traces through `MLFLOW_UI_URL`.
- **Model in Compose:** the LLM settings come from `.env` through Compose interpolation (no `env_file`, so a missing `.env` is not an error); without them the agent uses the `ollama` service. The `ollama` container ships without a model; pull one with `docker compose exec ollama ollama pull <model>`.
- **Pinned images:** `python:3.12.16-slim-bookworm`, `ghcr.io/astral-sh/uv:0.13.7`, `postgres:16.13-alpine`, `ollama/ollama:0.40.18`, `ghcr.io/mlflow/mlflow:v3.18.0`.

## Milestone 6

- **Added dependencies (npm):** `next`, `react`, `react-dom`, `typescript`, `tailwindcss` (from §4) plus what they need as `create-next-app@16.4.6` sets them up: `@tailwindcss/turbopack` (Tailwind's build plugin), `@types/node`, `@types/react`, `@types/react-dom`, and `eslint` with `eslint-config-next` (approved by the user). Locked in `web/package-lock.json`. No UI kit, data-fetching, or state library; components use plain React state.
- **No JavaScript test runner (approved):** the web app is checked by ESLint, `tsc --noEmit`, and `next build` in CI (`make lint`, `make web-build`), and by completing a run in a real browser against the Compose stack. The API behavior it relies on is covered by `tests/test_api.py`.
- **Browser calls the API directly:** the client bundle uses `NEXT_PUBLIC_API_URL` (default `http://localhost:8000`, baked in at build time) and the API allows the web origin through CORS (`CORS_ORIGINS`, default `http://localhost:3000`, GET/POST only). A Next.js proxy was not used because uploads can be up to 1 GB and proxied requests have body and time limits.
- **Client-rendered pages:** every page fetches from the API in the browser; Next.js only serves the bundle (`output: "standalone"`). `cacheComponents`, which `create-next-app` turns on, is off because there is no server-side data fetching.
- **API additions for the web app:** `GET /runs` (newest first, `limit` up to 200) so a run can be found again from the home page; `busy` on every run (the worker holds it, queued or running), because right after `POST /start` or a review the status has not changed yet and the page must keep polling; `filename` on each row-accounting entry of the report; and an edit that fails validation now names its target column (`Edit to plan: ...`), since one review can carry several edits.
- **Trace links fixed:** the Milestone 5 link (`/#/traces/<id>`) opens a "Page Not Found" in MLflow 3.18; the UI opens a trace at `/#/experiments/<experiment_id>/traces?selectedEvaluationId=<trace_id>`. Runs now store `trace_experiment_id` (Alembic migration `0002`), so runs traced before the migration have no link.
- **One upload request per file:** the page uploads files one at a time with `XMLHttpRequest` (fetch cannot report upload progress), so each file gets its own progress bar and its own error. A rejected file does not stop the others; the run starts only when every file is in.
- **Review screen:** one card per mapping, sorted by confidence (lowest first, missing columns first of all). Auto-approved mappings can also be edited or rejected. "Submit decisions and build" is enabled only when every proposed mapping has a decision. A required target with no source column can only be confirmed as missing (the API refuses an edit without a source column). Confidence colors follow the API's review routing (`needs_review`), not a threshold copied into the web app.
- **Failed runs:** the run page shows the error, a Resume button (`POST /start`), and the mappings, which can still be changed and rebuilt (`POST /review` accepts failed runs).
- **Defects tab is read-only:** the API has no defect decisions; defects are shown with plain-language names.
- **Pinned image:** `node:26.12.0-alpine3.23` for the web image. Next.js telemetry is off in the image and in the Makefile (`NEXT_TELEMETRY_DISABLED=1`).

## Milestone 7

- **Added dependency:** `httpx` (approved by the user) for `make pull-311`; Python's `urllib` fails HTTPS on the development Mac. It was already installed through `openai` and `mcp`, and moved from the dev group to the runtime dependencies.
- **Whole load waits for review (user's choice):** when the agent proposes a change, the recurring load stops in `awaiting_review` like an onboarding run and loads everything after review. A file with nothing to review is built and loaded at once, with no model call and no person. Warnings never hold a load.
- **One source per (customer, source name):** a source is saved from a finished onboarding run with exactly one file (`POST /runs/{id}/contract`); each save or changed load adds a version row to `mapping_contracts`. Besides the spec's columns, a version stores `target_schema` and its `mappings` (source column, target column, transform SQL). `runs.contract_id` points at the version a load was checked against; `runs.drift` holds its findings. Migration `0003`.
- **Recurring loads take one file** (`POST /contracts/{id}/loads`, field `file`), always against the latest version of the source, even when an older version's id is in the URL. Adding files to a recurring run is refused (409).
- **Source table:** one DuckDB file per source under `<DATA_DIR>/sources/<slug>-<hash>/warehouse.duckdb`, table named like the target, with the target's columns plus `loaded_at` and `run_id`, primary key on the target's unique column. Loads upsert (`INSERT … ON CONFLICT DO UPDATE`), so loading the same rows twice only refreshes the lineage columns. Saving a source also loads the onboarding run's rows. The report shows `inserted`, `updated`, and `total_rows`. The upsert runs in the API process after the build, like row accounting.
- **New contract version** after a load whose mappings or column fingerprint differ from the version it was checked against (after review, a repair, a rename, or a missing optional column). Its baseline is that load's file. Unchanged loads keep the version, so later files are compared with the last reviewed baseline.
- **Baseline profile:** per source column the inferred type, empty rate (blanks plus null tokens such as "N/A"), value shapes, and top values; per saved mapping the share of real values (not blank, not a null token) its transform fails on, and the failing values (`tools.transforms.check_values`).
- **How each check is decided** (`agent/drift.py`, no model call):
  - *Renamed:* a missing mapped column and an added column with the same inferred type whose value shapes or top values overlap by at least 50%. The saved transform is rewritten to read the new name (sqlglot) and proposed for a person to confirm. No model call: the old mapping is the proposal.
  - *Missing:* blocks the load when the column fed a required target (the run fails with "Load blocked: …" and never builds); otherwise a warning, and the target stays empty.
  - *Added:* the model proposes a target for the new column, or leaves it out.
  - *Type or format change:* the saved transform fails on more than 2 points more of the real values than at the baseline. New value shapes are listed as evidence. Comparing failure rates instead of shape lists avoids alarms on free-text columns, whose shapes vary from batch to batch.
  - *New category:* for targets with allowed values, real values the saved transform does not turn into an allowed value and that did not fail at the baseline. Rows still holding them after review are quarantined with `new category <column>` (recurring builds render that check into the checked model instead of failing `accepted_values`).
  - *Null rate jump:* more than 10 points above the baseline, and at least 3 standard errors (two-proportion z-test), so small files do not warn by chance. Without that guard, 60-row samples of `canceled_at` raised false alarms.
  - *Volume:* below 50% or above 200% of the average of the last 5 finished loads plus the baseline file.
- **Drift mapping:** the model sees only the changed columns' profiles, what changed (with the previous transform), and the saved mappings it must not touch. `submit_mappings` refuses targets that keep a saved mapping and source columns outside the changed set. Every proposal goes to review regardless of confidence, with the finding as the review reason.
- **Target table for NYC 311 (user-approved):** `service_requests` with request_id, created_at, closed_at, agency, complaint_type, descriptor, status, borough, incident_zip, latitude, longitude. `datagen.schemas.TARGETS` lists it next to the three generated tables; eval cases still cover only the generated ones.
- **`make pull-311`:** fetches one day (default yesterday) from Socrata with paging, writes `data/311/nyc311_<date>.csv`, and submits it through the API. The first time it starts an onboarding run for customer "NYC Open Data" (review it in the web app, then save it as source `nyc-311`); after that every run is a recurring load. A failed fetch writes no file.
- **Drift eval:** `make seed` also writes 33 drift cases (`evals/drift_cases/`, git-ignored): per table, three unchanged batches (fresh samples; any finding is a false alarm) and one batch per drift type, all 1,000 rows of clean data with the target column names, so only drift is tested. `make eval-drift` onboards each table's base batch with the answer key, saves one source per case, loads the case, approves the proposals the answer key expects, and scores detection recall and precision, false alarms, unchanged loads without a model call, correct outcomes (loaded, or blocked when it should be), and accepted proposals. `EVAL_ARGS=--fake` answers proposals from the answer key. CI does not run it; `tests/test_drift_eval.py` checks every generated case raises exactly its expected findings.
- **Web pages for recurring loads (user's choice):** `/sources` lists sources; `/sources/[id]` has a one-file drop zone that starts a load, the recent loads, the saved mappings, and the version history. A finished onboarding run has a "Save as recurring source" card (`saved_contract_id` on runs shows it was saved). Every recurring load shows a "What changed" panel.
